# Database foundation (ADI-173)

This phase introduces PostgreSQL 17 application tables, PostGIS, development
fixtures, and pgTAP integrity tests. It does not implement authentication,
client authorization policies, discovery, a booking API, or payment processing.
The Expo and TanStack Start applications remain independent and unchanged.

## Entities and relationships

All application tables are in `public`; trigger helpers live in the unexposed
`parkey_private` schema. UUID primary keys are generated by PostgreSQL, except
profiles, whose primary key is an existing Supabase Auth user ID.

| Table                   | Purpose and relationships                                                                          |
| ----------------------- | -------------------------------------------------------------------------------------------------- |
| `profiles`              | Minimal person/driver profile; one-to-one with `auth.users`. Also usable by staff.                 |
| `vehicles`              | Belongs to a profile; canonical plate and two-letter registration country unique per driver.       |
| `parking_operators`     | Organization, verification status, and verification evidence reference.                            |
| `operator_staff`        | Operator/profile membership with `owner` or `staff` role and optional revocation timestamp.        |
| `parking_locations`     | Belongs to an operator; address, WGS84 geography point, verification, and authorization reference. |
| `inventory_units`       | One dedicated space or one explicitly committed capacity unit at a location.                       |
| `operating_hours`       | Nonoverlapping weekly opening intervals per location and ISO weekday (Monday = 1).                 |
| `availability_blocks`   | Temporary closure for a whole location or a unit belonging to that location.                       |
| `reservations`          | Driver, owned vehicle, inventory unit, booking interval, explicit hold deadline, and status.       |
| `reservation_events`    | Automatically recorded initial/status events, optionally attributed to an Auth actor.              |
| `payment_references`    | Reservation-to-provider reference anchors, unique by provider/reference. Multiple per reservation. |
| `operational_incidents` | A location incident or a reservation incident; optional reporter and resolution timestamp.         |

Foreign keys restrict deletion to preserve booking/audit relationships. There is
no automatic deletion cascade from Auth users. Account erasure/anonymization and
retention must be designed before production. Foreign-key lookup columns have
indexes; booking exclusion constraints and the location spatial index use GiST.

`@parkey/shared-types` adds only the schema's four enum vocabularies as type-only
unions. These are not database clients, permission checks, runtime validators, or
full row/API contracts. Keep their literals aligned with migrations; generate
complete database types when an integration actually consumes them.

## Inventory and verification

Facility size is intentionally absent. A row of inventory is **one enforceable
Parkey allocation**, never an inference from a facility's total capacity:

- `dedicated_space` identifies a specifically committed bay.
- `capacity_unit` represents one token of an explicitly committed, enforceable
  capacity pool. A commitment of N spaces requires N units. It does not promise a
  particular physical bay; the operator must enforce the commitment on arrival.

Inventory defaults to uncommitted. Committing it requires a nonblank evidence
reference and a timestamp. Operator and location verification independently
default to `pending`; `verified` requires evidence and a timestamp. Location
approval evidence must cover the operator's authority to offer that location.
References identify future reviewed records/documents, not publicly accessible
URLs, secrets, or proof that the database independently verified a legal right.

A trigger admits an active reservation only when its inventory is committed and
both location and operator are verified. It locks those rows for share while
checking, preventing concurrent updates from invalidating the admission check
before commit. Suspension/withdrawal after admission preserves existing bookings
for explicit operational resolution; it blocks new active writes. A foreign key
also prevents choosing another driver's vehicle. Staff membership is structural;
it does not confer API/database permissions in this phase.

There is no public listing endpoint or bookable flag. In ADI-174/ADI-185, public
queries must expose only reviewed fields at verified operators/locations with
committed inventory. Staff must never grant themselves membership, verification,
or inventory authorization. Operator/location reassignment and changes to
existing reservations need protected server operations and historical handling.

## Time and intervals

Instants use `timestamptz`, with ISO 8601 UTC (`Z`) values in fixtures. PostgreSQL
stores absolute instants; clients display Asia/Manila. Location time zones are
restricted to Asia/Manila for this pilot. Weekly hours use local `time` values and
ISO weekdays. Split overnight opening intervals at midnight into separate days;
`24:00` is supported as a closing boundary. Missing hours mean no opening window,
not unrestricted availability. Blocks and bookings require finite, increasing
endpoints. Adjacent intervals use half-open `[start, end)` semantics.

No hold duration, grace period, price, commission, refund or cancellation rule
is inferred. A `held` reservation requires an explicit finite `hold_expires_at`
after its creation timestamp. Confirmed/history records may retain that deadline
for reference. Whether a hold deadline must precede the arrival time is a future
policy decision. Past reservations can be imported; the foundation does not
invent a restriction against historical records.

## Concurrency boundary for ADI-185

`reservations_no_active_overlap` is a PostgreSQL GiST exclusion constraint on
inventory unit ID and `tstzrange(starts_at, ends_at, '[)')`, filtered to `held`,
`confirmed`, and `checked_in`. Both provisional holds and confirmed reservations
occupy the same resource in the same table. Competing transactions cannot commit
overlapping active intervals for one unit, including reactivation and interval
updates. Different capacity tokens can be booked simultaneously. Terminal states
(`completed`, `cancelled`, `expired`, `no_show`) release the interval.

A clock tick cannot change an index predicate. An elapsed hold continues blocking
until a trusted transaction explicitly changes its state to `expired`. Do not
add `now()` to the constraint predicate or assume a cleanup worker is running.

The future booking engine must use a single transaction to:

1. Validate authenticated identity, vehicle ownership, membership/permissions,
   verification evidence, committed inventory, and the requested interval.
2. Lock operator/location/unit rows in a consistent order. Availability edits
   (hours, blocks, commitment, verification, inventory reassignment) must use the
   same locking protocol; locks serialize the validation against those edits.
3. Reclaim elapsed holds under lock, validate the entire requested interval
   against local opening hours and both unit/location blocks, and write the hold
   or reservation plus any required audit context atomically.
4. Respect the exclusion constraint and handle exclusion violations (`23P01`),
   deadlocks, and serialization failures with bounded retries where appropriate.
5. Treat `(driver_id, idempotency_key)` uniqueness as duplicate-request protection.
   Compare the original request payload before returning a previous result;
   uniqueness alone is not a complete idempotency API.

**Not enforced yet:** hours/block versus reservation conflicts, expiry scheduling,
allowed status transitions, arrival/no-show rules, actor authorization, pricing,
or payload-aware idempotent responses. Adding a closure does not automatically
cancel an existing booking. Frontend availability remains advisory. Explicit
multi-session race tests belong with the transactional booking entry point;
pgTAP here verifies the underlying constraint behavior in one transaction.

## Audit, payment and incident boundaries

Reservation insertions and status changes automatically append events in the same
transaction. Events capture prior/next status, database timestamp, and `auth.uid()`
when available. Backend maintenance without an end-user JWT has a null actor;
a complete staff/system reason and provenance model remains future work. Updates,
deletes and truncation of events are rejected by triggers. Events' restrictive
foreign key also prevents reservation deletion. This is status history, not an
audit trail for all profile, verification, inventory or payment edits. Privileged
schema owners can still disable triggers; they are a trusted operational boundary.

Payment references store identifiers only: no amounts, commission percentages,
checkout/session payloads, credentials or claim of successful payment. A later
payment feature must verify webhook signatures, deduplicate provider events, and
establish server-side reconciliation truth. An incident has exactly one subject;
a reservation incident derives its location through its inventory unit, avoiding
contradictory location links. Incident workflows and severity policies are deferred.

## Authorization boundary for ADI-174

Every application table enables RLS and has **no policies**. All table privileges
are explicitly revoked from `PUBLIC`, `anon`, and `authenticated`, including
truncate. Browser/mobile clients cannot read or write this data yet, even when
signed in. RLS would still deny row access if table grants were accidentally
introduced without policies. Private helper functions are security-invoker,
use an empty search path with qualified object names, and revoke client execution.
No security-definer RPC or publicly callable privileged function is introduced.

Migration owners and trusted Supabase service roles bypass RLS; never distribute
their credentials. No frontend SDK or keys are added. ADI-174 must introduce
reviewed table/column grants and operation-specific policies together, covering:

- driver-owned profiles/vehicles and reservation visibility;
- active operator memberships and operator-scoped locations/inventory;
- administrator permissions from a trusted server-managed source, never
  user-editable metadata or a self-assigned profile role;
- server-only reservation mutation, verification, payment and event operations;
- public discovery projections that exclude PII and authorization evidence.

Do not enable generic self-write policies on whole rows: drivers must not mutate
reservation status, inventory or verification merely because they own a profile.
Avoid exposing authorization decisions through stale JWT role claims alone.

## Local verification and fixtures

Follow [development setup](development.md#local-database-migrations-and-tests).
The migration is managed by the pinned Supabase CLI. `supabase/seed.sql` is
configured for local reset and contains only visibly fictional operators,
locations, evidence references, two committed units, one uncommitted unit,
sample weekday hours, and a sample closure. There are no fixture Auth accounts,
passwords, reservations, customer data, or payment records. Fictional verification
is a demonstration, not approval of a real facility. Never load this seed into a
hosted environment. Reset recreates it; rerunning the seed on an already seeded
database is intentionally not an upsert workflow.

`supabase/tests/database/foundation.test.sql` creates separate fictional test
identities and data inside a rollback transaction, without depending on seed
rows. It covers ownership/FKs, uniqueness, evidence requirements, spatial setup,
active overlap and adjacency, explicit expiry, status events and immutability,
hours, block scope, payment references, incident subjects, RLS flags, absence of
policies, client ACLs, and denied reads/writes with temporary test-only grants.
No test data or grants survive the transaction.
